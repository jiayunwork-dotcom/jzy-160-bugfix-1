上周五下班前，我往粘弹核算服务里丢了一个作业：材料档 E∞=3，两条支路 E=4、τ=0.1 和 E=6、τ=10，不带 WLF；十条阶跃保持历程，每条 0 到 100 秒、应变恒为 0.1，均匀输出网格 30000 点。周一回来一看，进度还停在 running，succeeded=9、failed=0，第十条仍是 pending，没有错误码也没有原因，之后再怎么等都不动。服务日志里倒是有一条 MongoDB 的 BSON 大小异常，可作业记录和那条历程上什么都没留下。把条数减到五条，或者点数降到几千，同样的作业几秒钟就 completed，数也对。

排查时还撞上另一件事。单独提交一条 40000 点的历程，要算将近十秒，这段时间里连查材料档这种跟计算无关的请求都要七秒才回来。点数从两万翻到四万，耗时从两秒出头涨到十秒左右，差不多是四倍。我们当初要这个服务，就是因为长历程在表格里卷积算不动，说好的逐步递推、计算量随步数线性增长，实际跑出来并不是这么回事。

修完我打算这么验：

上面那个十条、每条三万点的作业能跑到 completed，十条都 succeeded，每条的时间、应变、应力、松弛模量都能完整取回，跟把这一条单独提交一次得到的数完全一致。作业无论在哪一步出错，包括结果写不进库，都要落到终态：出问题的历程标 failed 并附原因，其余历程照常出结果，再也不能出现一直挂在 running 的作业。输出点数翻倍，计算耗时大体跟着翻倍，而不是翻四倍；大作业正在算的时候，建档、查进度、按材料档检索这几个接口仍然一秒内有响应。命名卷里升级前就存在的老作业，升级后还能查进度、取曲线、按材料档检索出来。查进度、取完整结果、按材料检索的路径和现有字段保持原样，调用方一行都不用改。

结果到底怎么存，是拆到别的集合、分块写，还是另有办法；单条历程和整个作业要不要设上限、设多大、超了怎么报；计算放在哪里跑才不会拖住其它请求。这几件事我没有现成答案，请你权衡后各定一个做法，在 README 里讲清楚为什么这么选，被放弃的那条路本来能换来什么、又要多付出什么。

σ(t)、E(t)、储能与损耗模量这些数值一个都不许变，现有单元测试照旧要过。上面每一条验法都补上对应的测试，大作业那条要在真实 MongoDB 上跑过，不能只拿测试替身糊弄。
